# Getting started

Everything here runs on a Jetson AGX Orin on JetPack 6.2.1 (abra). The images are arm64 only.

## Build

From the repo root:

```bash
make build                                         # yoloe, rfdetr and sam3, tagged :dev
make yoloe                                         # one image
make yoloe INTERFACES=../rammp-interfaces-ros2     # against an unreleased interfaces checkout
```

Every Dockerfile builds from the repo root, because the images share `object_detection/common/` and `object_detection/config/`.

## Run a scene segmenter by hand

```bash
docker run --rm --runtime nvidia --network host --ipc host \
  -v rammp_perception_engines:/cache/engines \
  ghcr.io/rammp-org/rammp-perception/yoloe:dev \
  --ros-args -p model:=yoloe-26s-seg -p device:=dla0
```

On abra the bench keeps DDS on loopback. Pass its Cyclone config the way sheppy does, or the node discovers the
camera topics but receives no frames:

```bash
C=/home/abra/.config/rammp-bench/cyclonedds-local.xml
docker run ... -e CYCLONEDDS_URI=file://$C -v $C:$C:ro ...
```

The first start of a YOLOE configuration builds its TensorRT engine; the log says so and how long to expect.
Once running, the node logs its rate, latency and objects per frame every 10 seconds.

## Look at the output

```bash
ros2 topic hz /perception/object_detections
ros2 topic echo --no-arr /perception/object_detections
```

`/perception/scene_segmenter/overlay/compressed` shows the masks on the camera frame in Foxglove or `rqt_image_view`.

## Run the odom3d tracker by hand

odom3d sits between the scene segmenter and `/perception/object_detections`; see the
[interface reference](/rammp-perception/interface#odom3d-tracker). Build both images with `make rfdetr odom3d`: the
rfdetr image needs a build that carries `classes_tracking.yaml`. Run the segmenter with low thresholds, without its
own tracker, publishing on the raw topic:

```bash
docker run --rm --runtime nvidia --network host --ipc host \
  ghcr.io/rammp-org/rammp-perception/rfdetr:dev \
  --ros-args -p classes_file:=/etc/rammp/perception/classes_tracking.yaml -p tracking:=false \
  -r /perception/object_detections:=/perception/object_detections_raw
```

Then odom3d. It needs depth registered to the color frames, the color camera's `camera_info`, and TF from `odom`
to the camera at image stamps. Point `depth_topic` at the camera's registered depth. Set `camera_extrinsic` only if
the TF tree has no `base_link` → camera link (the value below is the flatbot's):

```bash
docker run --rm --network host --ipc host --user 1000:1000 -e HOME=/tmp \
  ghcr.io/rammp-org/rammp-perception/odom3d:dev \
  --ros-args -p depth_topic:=/scene_camera/depth/image_raw \
  -p "camera_extrinsic:=[0.8257, -0.2643, 0.9228, -0.5316, 0.5441, -0.4426, 0.4747]"
```

Pass both the bench's Cyclone config, as for the segmenter above. To check it:

```bash
ros2 topic hz /perception/object_detections_raw   # the segmenter, at its frame_stride rate
ros2 topic hz /perception/object_detections       # odom3d, at the camera's rate
ros2 run tf2_ros tf2_echo odom base_link          # odometry must be live
```

odom3d logs every 10 seconds: input and output rates, update and render times, live tracks, and what it had to
skip (no TF, no depth for a detection). `/perception/odom3d/markers` shows the tracked 3D boxes in RViz or Foxglove,
with `odom` as the fixed frame.

## Run it under sheppy

Each `rammp-alternative.*.yaml` at the repo root is an alternative for a deployment manifest's `scene_segmenter`
node (or the `sam3` node), with `scene_segmenter_mock` as the hardware-free stand-in. Copy the ones you want into
the node's `alternatives:` list in rammp-deployments, then pick one in the profile.

## Without a GPU

`--ros-args -p mock:=true` loads no model and publishes empty results on the real topics. `make smoke` runs every
detector image that way and checks it publishes and exits on SIGTERM.
